# Incident: `npm test` on a fresh branch from `origin/main` wrote real data to production (2026-09-07)

> See also [`INCIDENT_2026-09-06.md`](INCIDENT_2026-09-06.md) — the original
> incident this guard was built to prevent. This is a **repeat of the same
> class of incident, one day later, via a different path**.

## Root cause

The fix for the 2026-09-06 incident (`tests/live/liveGuard.js`, the
`jest.config.js` exclusion, and moving `tests/integration.test.js` to
`tests/live/integration.test.js`) existed only as two local, unpushed
commits on a branch called `fix/local-tests-no-prod-writes`. It had not
been merged — or even pushed — to `origin/main`.

While working a separate, unrelated fix (Math Stars practice-points
rounding), I intentionally created a **new branch cut from `origin/main`**
rather than stacking on top of `fix/local-tests-no-prod-writes`, specifically
to keep the two unrelated changes cleanly separated for review. That
reasoning was sound for keeping the diffs clean, but it had a side effect I
didn't check for first: `origin/main` still had the *pre-fix* repo state —
`tests/integration.test.js` sitting unguarded at the repo-root `tests/`
level, hardcoding `https://dailymathforkids-api.vercel.app`, with no
`liveGuard` import and no opt-in check — and `jest.config.js` on that base
had no `testPathIgnorePatterns` entry excluding it.

I then ran a bare `npm test` on that branch (intending only to sanity-check
that the Math Stars fix hadn't broken anything, in what I believed was a
clean baseline) instead of scoping it to `tests/math-stars.test.js` the way
I had been doing on the branch that already had the guard. Jest's default
`testMatch: ['**/tests/**/*.test.js']` picked up `tests/integration.test.js`
along with everything else, and it ran to completion against production
(all 17 of its test cases passed).

**In short: creating a clean branch from `origin/main` silently removed the
not-yet-merged safety guard, and a bare `npm test` — a command that's safe
by design once the guard is merged — then executed the same unguarded
production-writing integration test as the original incident.**

## Confirmed effects

Read directly from the (pre-fix) `tests/integration.test.js` code that ran,
which is byte-for-byte the same test logic as the 2026-09-06 incident (same
file, just not yet moved/guarded) — so the effects are the same shape:

- **Two `users` rows were created** via real `POST /api/register` calls,
  nicknames matching `test_<6-char base36 timestamp>_kid` (Grade 3, security
  question "What city were you born in?"/"Toronto" at registration, then PIN
  and security question changed twice more via real `POST /api/set-pin` and
  `POST /api/forgot-pin` calls — final state: PIN `4321`, security question
  "What is your pet's name?", answer "Max") and `test_<same timestamp>_kid2`
  (Grade 5, `parent_email: "testparent@example.com"`, no security question).
- **No other tables were written** — same reasoning as the 2026-09-06
  incident: this test file only calls `/api/register`, `/api/lookup`,
  `/api/set-pin`, `/api/forgot-pin`, and `/api/forgot-nickname`.
- The `afterAll` cleanup hook logged
  `[cleanup] SUPABASE_SERVICE_ROLE not set — test accounts left in DB.` —
  `SUPABASE_SERVICE_ROLE` was not set in the shell, so no cleanup ran.

## What I could not determine, and why

Same limitation as 2026-09-06: the base36 timestamp suffix is generated at
run time and isn't logged by the test itself. I only captured a `tail -30`
of the run's output, which cut off before any per-test detail. I don't have
database read access and didn't request any, so I can't report the exact
nicknames, user IDs, or timestamp — and I'm not guessing at them here.

## What was NOT done

Per explicit instruction, I did not call `/api/cleanup-tests` or make any
further live API calls after discovering this, and did not attempt to
identify the exact rows via any read endpoint. Cleanup is left entirely to
manual review and action outside this session — see
`INCIDENT_2026-09-06.md`'s "Proposed cleanup" section for the same
narrow-identify-then-delete approach, which applies equally to whatever rows
this run produced (they'll be the most recent rows matching that query, not
the ones already identified from the prior incident).

## Fix

This incident is the direct motivation for the defense-in-depth layers added
in this same change (see `tests/live/liveGuard.js`'s header comment and
`tests/no-prod-in-default-run.test.js`):

1. The file-location exclusion (`tests/live/`) is now itself regression-tested
   against jest's *actual computed test list* (`jest --listTests`), not just
   assumed to work — see `tests/no-prod-in-default-run.test.js`.
2. The module-scope guard call in every `tests/live/` file means even a
   direct, explicit invocation of that file can't reach production without
   the opt-in env vars, regardless of jest config.
3. Reaching the specific production host now requires a *second*, separate,
   exact-hostname acknowledgement (`CONFIRM_PRODUCTION_LIVE_TESTS`) beyond
   the general `ALLOW_LIVE_TESTS` opt-in — so no single flag or env var
   flip can reach production by accident.

**The one thing none of these layers can fix by themselves: `origin/main`
itself was the unsafe artifact here, not a stale local branch.** Until this
PR (or an equivalent fix) is merged into `main`, *any* fresh clone or branch
cut from `origin/main` remains exactly as unsafe as it was on 2026-09-06.
Merging this promptly, rather than leaving it as an unpushed local branch,
is itself part of the fix.
