# Incident: local `npm test` wrote real data to production (2026-09-06)

## What happened

While verifying the practice-scoring flow for a separate feature review, I
ran `npm test` in this repo from a local shell. At the time, `npm test`
ran every `*.test.js` file under `tests/`, which included
`tests/integration.test.js` (since moved to `tests/live/integration.test.js`
— see the fix in this same branch). That file makes real HTTP calls against
`https://dailymathforkids-api.vercel.app` and registers real accounts as
part of exercising the registration/login/PIN-recovery flow.

Its `afterAll` cleanup calls a purpose-built `/api/cleanup-tests` endpoint,
but only if `SUPABASE_SERVICE_ROLE` is set in the environment. It was not
set in the shell I ran the command from, so cleanup was skipped and the
console printed:

```
[cleanup] SUPABASE_SERVICE_ROLE not set — test accounts left in DB.
```

**This is pre-existing, intentional CI behavior** (see `git log` on
`.github/workflows/test.yml` / `tests/integration.test.js` /
`api/cleanup-tests.js` — the `integration-tests` job has run this against
production on every push/PR to `main` since it was added, relying on a CI
secret for cleanup). Running it locally without that secret is what left
residue. The fix on this branch (see `tests/live/liveGuard.js`) prevents
this from happening again, locally or in CI, without an explicit
non-production target.

## Confirmed effects

Read directly from `tests/integration.test.js`'s code (not from database
access, which I don't have and didn't request):

- **Two `users` rows were created** via real `POST /api/register` calls,
  with nicknames matching the pattern:
  - `test_<6-char base36 timestamp>_kid` — Grade 3, registered with a
    security question (no parent email). During the same run, this
    account's PIN and security question were changed twice more via real
    `POST /api/set-pin` and `POST /api/forgot-pin` calls (final state: PIN
    `4321`, security question "What is your pet's name?", answer "Max").
  - `test_<same timestamp>_kid2` — Grade 5, registered with
    `parent_email: "testparent@example.com"` (IANA-reserved example
    domain — see "Side effects checked" below), no security question.
- **No other tables were written.** `tests/integration.test.js` only calls
  `/api/register`, `/api/lookup`, `/api/set-pin`, `/api/forgot-pin`, and
  `/api/forgot-nickname` — never `/api/submit`, `/api/practice-submit`,
  `/api/groups`, or any opt-in endpoint. I read the full file to confirm
  this; there is no code path in it that would create `submissions`,
  `practice_submissions`, `mistakes`, `groups`, `group_members`, or
  `reward_milestones` rows.

## What I could not determine, and why

- **Exact nicknames / user IDs / timestamp:** the base36 timestamp suffix
  (`Date.now().toString(36).slice(-6)`) is generated at test-run time and
  was never printed to my terminal (I only captured a `tail -80` of the
  run's output, which cut off before any per-test detail, and the test
  itself never logs the generated nickname). I do not have database read
  access and did not request any, per your instructions, so I cannot look
  it up directly. An attempt to bound the timestamp using local Jest cache
  file mtimes was inconclusive (the cache directory I found was several
  days stale, from an unrelated earlier session) and I'm not reporting a
  guessed value.
- **Exact run time:** I can only say this happened during the local test
  run in that work session; I don't have a reliable logged timestamp to
  cite. I'm intentionally not fabricating one.

## Side effects checked (not just "possible" — verified by reading the code paths actually exercised)

- **No email was sent.** `api/register.js`, `api/forgot-nickname.js`,
  `api/forgot-pin.js`, and `api/set-pin.js` contain no email-provider
  (`resend`) import or call — all four are pure Supabase read/write
  handlers. Email sending only exists in `api/weekly-email.js` and
  `api/send-prize-email.js`, neither of which this test file calls. The
  `parent_email: "testparent@example.com"` value is also IANA's
  reserved documentation domain (RFC 2606) and would not deliver mail even
  if something did try to send to it.
- **No points, submissions, or reward-milestone effects** — confirmed above
  by reading which endpoints were called.
- **Minor, low-likelihood, read-only note:** the test's "recovers nickname
  via parent email" case queries `forgot-nickname` by
  `parent_email = 'testparent@example.com'`. If any unrelated pre-existing
  account happened to share that exact placeholder email, that lookup would
  have returned its nickname in the test's own (not persisted anywhere)
  response. This is a read, not a write, and pre-exists this run — noted for
  completeness, not as a new effect.

## Proposed cleanup (NOT executed — for your review and your own action)

I have not called `/api/cleanup-tests` or any other write endpoint, and
won't. A **broad** deletion of everything matching `test_`/`E2E_` (what
`/api/cleanup-tests` does today) is explicitly not approved, since it would
also remove any legitimate historical rows from prior CI runs or other
testing you may want to keep or review first. Proposed narrow approach,
for you to run with your own Supabase access:

**Step 1 — identify (read-only), in the Supabase SQL editor:**
```sql
select id, nickname, grade, parent_email, security_question, created_at
from users
where nickname ~ '^test_[a-z0-9]{6}_kid2?$'
order by created_at desc
limit 10;
```
This pattern is deliberately narrower than `cleanup-tests.js`'s
`^(test_[a-z0-9]+_|E2E_)` — it matches only the exact
`test_<6chars>_kid` / `test_<6chars>_kid2` shape this specific test file
produces, not every historical test-prefixed row. It will still match rows
from *any* run of this same test file (today's and any prior run), since
the shape is identical every time — use `created_at` to pick out the most
recent one(s) as today's.

**Step 2 — confirm, then delete only those specific IDs:**
```sql
-- Replace <id1>, <id2> with the exact ids confirmed in Step 1.
delete from submissions where user_id in ('<id1>', '<id2>');  -- expected: 0 rows, included for safety (no ON DELETE CASCADE on this table)
delete from users where id in ('<id1>', '<id2>');
```

I'm not providing a version of this that runs automatically or that I could
run myself — it needs your own credentialed access and your confirmation of
the exact rows in Step 1 before Step 2 touches anything.
